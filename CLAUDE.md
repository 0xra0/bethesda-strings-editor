# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the Application

This project uses the **conda** environment `bethesda-strings-editor` (Python
3.10) for everything — running the app, the test suite, and any install. Do not
use the system interpreter or `pip` outside the env; it has a different and
incomplete set of packages.

```bash
conda activate bethesda-strings-editor
python main.py

# non-interactively (one-shot commands):
conda run -n bethesda-strings-editor python -m pytest tests/
```

Dependencies are in `requirements.txt`:

```bash
pip install -r requirements.txt
# Core:     PySide6>=6.11, requests>=2.33, cryptography>=48.0, anthropic>=0.104
# Optional: keyring, curl-cffi, py7zr, rarfile, hunspell/spylls — each has a
#           runtime fallback, so the app starts without them
```

Logging goes to both stdout and `translator.log` in the project root.

## Ollama Models

Three Modelfiles are tracked. **None of them names a real GGUF** — every `FROM`
is a `/path/to/…` placeholder, because the fine-tunes are not published and a
machine-specific absolute path is worse than useless to anyone else (and rots
here too: both previously-committed paths are gone from this machine). Point
`FROM` at a GGUF you have, then `ollama create <name> -f <file>`.

**Parameter precedence** is the thing to get right when editing them, and it is
per-model, not global. The app always overrides `system`, `temperature`,
`num_ctx` and `num_predict`; for the sampling knobs it sends
`top_p`/`top_k`/`min_p`/`repeat_penalty`/`repeat_last_n` **only when the model's
own profile in `OllamaWorker.MODEL_CONFIGS` defines that key** (`ollama_worker.py`
`payload["options"]` loop). No profile defines `min_p` or `repeat_last_n`, so
those always come from the Modelfile; `top_k` comes from the Modelfile for
`gemma4-*` (that profile omits it) but is overridden for `translategemma3-st`.
`num_predict` is adaptive per string —
`max(profile_num_predict, min(settings.ollama_num_predict, max(512, input_len × 4)))`
— so a profile's `num_predict` acts as the floor, not the cap. Profile lookup is
exact name → base-name prefix → `_DEFAULT_MODEL_CONFIG`, which is why a model
called `gemma4-opus48-st` picks up the `gemma4` profile (and its `think=false`).

### Translation model (`translategemma3-st` — `Modelfile`)

```bash
ollama create translategemma3-st -f Modelfile
```

Gemma 3 chat template. Any compatible instruct GGUF works — e.g. the public
[MamayLM Ukrainian model](https://huggingface.co/INSAIT-Institute/MamayLM-Gemma-3-12B-IT-v2.0).

### Reasoning model (`gemma4-opus48-st` — `Modelfile.gemma4-opus48`)

```bash
ollama create gemma4-opus48-st -f Modelfile.gemma4-opus48
```

Gemma 4 12B IT fine-tuned on Claude Opus reasoning data
([model card](https://huggingface.co/yuxinlu1/gemma-4-12B-it-Claude-4.6-4.8-Opus-GGUF)).
Has a thinking channel; the app sends `think=false` **and** strips `<think>…</think>`
in post-processing, so keep the `{{ if .Think }}` guard in the TEMPLATE.

### Quality-check model (`qcgemma4-st` — `Modelfile.qc`)

Gemma 4 E4B IT fine-tuned on `scripts/qc_dataset_sharegpt.jsonl` (14,928
examples, 16 issue codes).

```bash
ollama create qcgemma4-st -f Modelfile.qc
```

Driven by `ai_qc_worker.py`, which is a **separate, much smaller** call path than
translation: plain `/api/generate` with its own `_SYSTEM_PROMPT` (kept identical
to the Modelfile's `SYSTEM`), `temperature 0.0`, `num_predict 1024`, and nothing
else — so `num_ctx 8192` and the stop tokens come from the Modelfile. The model
name is free-form (`AppSettings.ai_qc_model`, default `qcgemma4-st`). `num_predict
1024` gives the chain-of-thought room before the VERDICT block; a truncated
verdict parses as *no issues found*, which is the one failure a quality checker
must not have. Input format matches the training data:
`Check this Ukrainian translation:\n\nSource (English):\n{src}\n\nTranslation (Ukrainian):\n{tgt}`.
Output is `VERDICT: GOOD` or `VERDICT: ISSUES_FOUND\nCODES: …\nSEVERITY: …\nDETAILS:\n- …\nACTION: AUTOFIX|RETRANSLATE`.

## Compiling UI Translations

UI translations live in `gui/translations/<locale>.ts` (source) and `.qm` (compiled binary). Supported locales: `uk_UA`, `de_DE`, `es_ES`, `fr_FR`, `ko_KR`, `pl_PL`, `cs_CZ`. After editing any `.ts` file:

```bash
./scripts/compile_translations.sh
```

## Architecture

### Two-layer structure

**`bethesda_strings/`** — pure Python parsing library, no Qt dependency:

- `core.py` — `BethesdaStringFile` / `StringDataObject`: binary parser/writer for `.strings`, `.dlstrings`, `.ilstrings`. Header is 8 bytes; each directory entry is 8 bytes (ID + relative offset). `.dlstrings`/`.ilstrings` have a 4-byte length prefix per string; `.strings` use null termination.
- `esp_handler.py` — `EspFile`: parses ESP/ESM/ESL plugin files. Only handles *non-localized* plugins (text stored directly in field buffers). Localized plugins (bit 0x80 in flags) use companion `.strings` files instead. Translatable field/record combinations are in `_FIELD_DEFS` (incl. `GPOF`/`GPOG` GameplayOption settings-menu titles). A resource-path safety filter (`_looks_like_resource_path`) skips values that are actually asset paths (backslash or known asset extension — e.g. a `DOOR/CNAM` animation path) so they aren't translated and break the mod, and `_SYNTHETIC_CONTEXT` attaches an anti-hallucination note to `QUST/FULL` quest titles when the record carries no real NLDT developer note. Extraction (`_parse_record`) and write-back (`_patch_fields`) line entries up purely by *"the Nth occurrence of this field signature in this record"* — a single record repeats one signature many times (a WEAP's `FULL` names the weapon, then every OBTE/OBTF modification grade) — so both **must** decide "does this occurrence count" with the same predicate, `_field_translatable_text()`; when they disagree, every later occurrence in the record shifts a slot and silently receives another field's translation (the write-back side used to skip only a lone `b"\x00"`, counting the empty-with-padding and resource-path occurrences extraction had dropped). For the same reason `save()`'s occurrence counter advances for **every** entry in `self.strings` (which is in physical file order), not only ones whose translation differs from the original — a proper noun deliberately kept as-is would otherwise desync the map from that point on. Also exposes module-level `scan_vmad(path)` / `apply_vmad_translations(path, edits)` (independent of `EspFile`, so they work on *both* localized and non-localized plugins): a GRUP-aware walk that decompresses record bodies, finds the `VMAD` field, parses script-property strings and rewrites only edited string spans — recomputing record + parent GRUP sizes and re-compressing compressed records. Writes a `.bak` before saving. See `vmad_handler.py`.
- `vmad_handler.py` — pure-Python VMAD (Papyrus script attachment) parser/classifier/safe-editor. `parse_vmad()` never raises (sets `fully_parsed=False` on truncation). Collects only String (type 2) and ArrayString (type 12) property *values* — never script/property *names* (editing those breaks binding). `classify_string_property()` tags each value `RISK_TRANSLATABLE` / `RISK_REVIEW` / `RISK_LOCKED` (resource paths/extensions/identifiers/event names → locked; multi-word phrases & text-named props → translatable; ambiguous single tokens → review). `replace_strings()` is a byte-splice editor: only edited value spans (and their 2-byte length prefixes) are rewritten, every other byte is copied verbatim, so unmodelled VMAD sub-structures (QUST aliases, script fragments) survive untouched. `find_vmad_field()` locates the VMAD payload in a decompressed record body (XXXX-oversize aware).
- `ba2_handler.py` — `BA2File`: reads BA2 archives (GNRL type only, zlib-compressed). Supports Fallout 4 v1 and Starfield v2 formats. Used to open `.strings` files bundled inside BA2 archives.
- `wwise_voice.py` — `VoiceIndex`: maps a Starfield dialogue **FormID → original voice clip** packed inside `*Voices*.ba2` archives. Starfield ships voice as Wwise `.wem` (RIFF/WAVE, Vorbis tag `0xFFFF`) at `sound/voice/<plugin>.esm/<voicetype>/<8hex-formid>.wem` — *not* `.fuz` like Skyrim/FO4. One FormID maps to several voice types, so `find()` returns a list. `ffmpeg` cannot decode `.wem`; `get_wav()` shells out to `vgmstream-cli` and caches the decoded WAV. Pure helpers: `classify_archive_language()` (no `_xx` suffix = English base game), `form_id_from_name()`, `voice_type_from_name()`.
- `xml_handler.py` — `XMLHandler`: imports/exports xTranslator SST XML format (match by `sID` hex first, fall back to `Source` text — mirrors xTranslator's Pascal logic).
- `encoding.py` — `EncodingConverter`: encoding detection and conversion (UTF-8/CP1251/CP1252/BOM).
- `operations.py` — factory functions for `BethesdaStringFile.filter_and_modify()`.
- `version_diff.py` — `VersionDiff`: computes per-string diff between two versions of the same file (added/removed/changed). Used by the version comparison dialog and batch folder comparison.
- `esp_diff.py` — ESP/ESM **mod-update migration**: the plugin-file counterpart of `version_diff` (which keys on a flat string ID). Diffs two versions of a plugin keyed on `(form_id, record_sig, field_sig, occurrence)` — FormIDs are stable across mod releases, so the same logical string matches between e.g. `MyMod.esp` v1.0 and v1.2. `compute_esp_diff(old, new, translated)` classifies ADDED/REMOVED/MODIFIED/UNCHANGED and attaches the prior translation (read from the previously-translated plugin's `.original`, since saved translations live in the field buffers). `build_migration_items()` returns `(form_id, record, field, occ, translation)` tuples for UNCHANGED strings so they carry forward verbatim. `index_by_key()` is shared by the GUI to match migration items to loaded table rows. Pure Python (no Qt); reuses `DiffStatus` + `_REPORT_CSS` from `version_diff`.
- `triplet.py` — `TripletReference`: read-only companion holder for a `.strings`/`.dlstrings`/`.ilstrings` triplet. **The three files have INDEPENDENT string-ID spaces** — the same numeric ID is a *different* string in each (the engine picks the file from the field type, not the ID). They must therefore never be merged/deduped into one `BethesdaStringFile`: doing so drops same-ID/different-type strings and writes a file contaminated with foreign IDs (game then shows `<Error: Unknown lstring ID …>`). `add_file()` copies out decoded text only (never retains/mutates the source objects), keyed by extension so ID spaces stay separate; `lookup(ext, id)` resolves within one space. Used by `main_window._offer_triplet_load` (companions load as read-only reference, never appended into the saved file) and `companion_strings_dialog`.
- `strings_validator.py` — pure `validate_translation(source_index, translated_index)`: classifies each `(base, ext)` file as `missing` / `parse_error` / `empty` / `incomplete` / `orphan` / `ok` by comparing the ID sets the game's source files contain against the translation's. `will_error_in_game` flags the ones that produce in-game `<Error: Unknown lstring ID …>`; `extra_ids` on an `ok` file surfaces cross-file-type contamination. The caller builds the ID indexes (from loose files + `.ba2` archives); this module only classifies. Front-end: `validate_translation_dialog`.
- `official_tm_miner.py` — **Official-TM miner**: builds an authoritative TM + glossary from the base game's *own* official localizations, with zero AI calls. Bethesda ships every supported language for a plugin side-by-side, **aligned on identical string IDs**, in one archive (Starfield's `Starfield - Localization.ba2` holds `starfield_en.strings` … `_de` … `_pl` … keyed identically per extension), so aligning EN against an official target by `(base, ext, id)` yields Bethesda's canonical rendering of every weapon/faction/UI-verb/quest term. `scan_language(data_dir, lang)` decodes every `<plugin>_<lang>.<ext>` (BA2 first, loose fills gaps) into `{(base, ext): {id: text}}`; `available_languages()` lists what's present; `align_indexes(src, tgt)` matches only IDs non-empty in both (alignment is always *within* one `(base, ext)` — the three extensions have **independent ID spaces**, see `triplet.py` — and requiring both languages present is what restricts mining to officially-localized content); `build_tm_pairs(aligned)` dedups by source (majority target on conflict) and **drops identity pairs by default** (`include_identity=False` — a source the target left in English would otherwise "translate" EN→EN and pre-fill a row as *translated* while still English); `mine_glossary(aligned)` selects the short term-like subset (drops editor-IDs/paths/sentences via `_looks_like_identifier`/`_is_glossary_source`, `min_consistency` on the dominant target, optional `reference_indexes` annotate each candidate with other langs — e.g. Polish as a Slavic cross-reference for a non-shipped Ukrainian target). `mine_official(data_dir, source_lang, target_lang, *, reference_langs=…, progress=…)→MineResult(tm_pairs, glossary, plugin_count, aligned_pairs)` is the GUI worker entry point. Pure Python (no Qt). Front-end: `official_tm_dialog`.

- `swf.py` — low-level **SWF container primitives** shared by `font_checker` (glyphs + advance widths) and `swf_widgets` (UI widget bounds): `decompress_swf` (FWS/CWS; refuses LZMA `ZWS` rather than guessing), `iter_tags` (walks a tag stream — pass `start=4` to walk a nested **DefineSprite** body, which is itself a tag stream), `read_rect`/`skip_matrix` (SWF's bit-packed types can't be read with `struct`), `read_cstring`, `stage_size`. Everything is in **twips** (`TWIPS = 20`, i.e. 1/20 px) and returned raw so nobody double-divides. Nothing raises on malformed input — game files get truncated, re-packed and modded, and a scan must degrade rather than crash.
- `font_checker.py` — `FontChecker`: glyph **coverage** + horizontal **metrics** from Bethesda font sources (Scaleform SWF `DefineFont2`/`DefineFont3` tags, TTF/OTF, `fontconfig.txt`), plus a built-in conservative safe set. Answers "can the game *draw* this character?" — `missing_chars()` finds text that renders as tofu (□), `SUGGESTED_FIXES`/`apply_fixes()` substitute safe equivalents. It also parses the **advance widths** `width_fit` needs: `FontSource.advances` maps codepoint → advance as a **fraction of the EM square**, normalised at parse time so callers never see raw font units — SWF advances come from the `FontAdvanceTable` (present **only** when the tag's `HasLayout` flag `0x80` is set, so a font can legitimately have glyphs but no widths → `has_metrics` is False rather than guessed), and the EM square differs by tag (`_SWF_UPEM_DEFINEFONT2` = 1024 vs `_SWF_UPEM_DEFINEFONT3` = 20480, since DefineFont3 stores coordinates 20× larger — reading one with the other's constant is a silent 20× error). TTF advances come from `hmtx`, indexed by glyph id, which is why `_read_cmap4`/`_read_cmap12` return `{codepoint: glyph_id}` maps rather than bare codepoint sets. `parse_fontconfig` reads Bethesda's font manifest — note its `map "$MAIN_Font" = "RF_35_M" Normal` syntax has an **`=`**, which `_MAP_RE` originally did not allow, so every mapping in a real `fontconfig.txt` was silently dropped; the `=` is optional in the regex because older Bethesda titles omit it. That map is what lets `swf_widgets`/`width_fit` resolve a text field's font **class** (`$MAIN_Font_Bold`) to a real **family** (`RF_55_M`) and thus to the right bundled face. Front-ends: `font_checker_dialog`, `width_fit_dialog`.
- `swf_widgets.py` — **real UI widget bounds, read out of the game's own SWFs**. `width_fit` measures a label's width exactly, but a budget to compare it against cannot come from a `.strings` file — the game supplies it, in the `DefineEditText` tag of every menu. What is ground truth here is carefully bounded: **bounds + margins are exact** (`usable_width_px` = authored width − margins, i.e. the space text actually gets); **clip behaviour is exact** and is what makes a field length-critical (`clips` = no Multiline, no WordWrap, no AutoSize → text physically cannot reflow, so it truncates — no heuristic needed); **font face is exact given a fontconfig** (fields name their font by *class*, which `parse_fontconfig` maps to a family we ship); but **font size usually is not** — Starfield leaves `HasFont` clear and sets size from ActionScript, so across the shipped Interface SWFs only ~4 % of clipping fields declare one (in their HTML initial text, `<font size="18">`). Hence `FontSizeSource.DECLARED` vs `DERIVED` (inferred from box height via `_HEIGHT_TO_FONT_PX = 1.22`, calibrated on the 24 shipped fields that state both; spread 1.15–1.44). The distinction is carried on every record and never flattened, **because width scales linearly with font size — a 20 % size error is a 20 % error in the verdict**. `parse_edit_text` consumes the tag's chain of *optional* flag-gated fields in order (skip one present field and every byte after it is misread). A field has no name of its own, so `_collect_names` joins **SymbolClass** (names the sprite) to the **PlaceObject2/3** instance name inside its **DefineSprite** body → `BasicButton_Label.Label_tf`. `scan_game_ui(data_dir)` reads loose `Interface/*.swf` **and** `*Interface*.ba2` (loose shadows archived, exactly as the game and localisation mods resolve them), yielding a `WidgetCatalogue` (~250 SWFs, ~4600 fields, ~2560 clipping on a real install); `dedupe` collapses the same component compiled into dozens of menus. `is_measurable` drops **zero-width** fields — a 0 px box is not a tiny widget but one ActionScript sizes at runtime, and measuring against it would flag *every* string. **Large-font worst case**: Starfield ships a `*_lrg` accessibility build of most menus (`missionmenu_lrg.swf`) where the box is usually the *same* size while the font grows (up to **×2.64** — `missionmenu › text_tf` goes 18px → 48px in an unchanged 869px box), so a label that only just fits the standard menu clips there. It is **not** universally tighter and nothing may assume it is: of the 589 widgets defined in both builds, 251 grow the font, 336 keep it, and **2 actually shrink it** (`missionboard › text_tf` goes 49px → 26px). So the worst case is per widget, decided on **`capacity_em`** (`usable_width ÷ font_px`) — pixel width alone would call the two builds identical and miss the entire point — and `catalogue.worst_case_with_reason(field)` returns *which* build it picked **and why** (`VariantOutcome.TIGHTER` / `NO_TIGHTER` / `AMBIGUOUS` / `NO_VARIANT`), because three of those four leave the field unchanged and a caller that reports them all as silence tells the user nothing about whether the accessibility build was checked at all. The pairing key (`_variant_key`) is `(base_swf, field_name, usable_width)` and deliberately **not** the character id (the menus are compiled separately so ids drift; pairing on them yielded a "pair" whose large-font build was *smaller*) — but the box key alone is **not sufficient either**: one menu commonly reuses a field name for several boxes of the same width (`text_tf` appears 146×), so `variants()` requires an **unambiguous 1:1** standard↔large pairing and otherwise refuses (`AMBIGUOUS`). Without that guard the key silently grouped *unrelated fields in the same menu* and measured against the tightest: `chargenmenu › text_tf` (844px @ 29px) was checked against a **126px title** in the same menu — a six-character budget that flags every translation as clipping — and 33 widgets "swapped" to a build that was not the large-font one at all. Which field draws which string is **not** knowable from here — a `.strings` entry has no link to a SWF field — so this supplies the catalogue and the *user* picks the widget. Pure Python (no Qt). Front-end: `width_fit_dialog`.
- `width_fit.py` — **UI width-fit simulator**: the question *after* glyph coverage — "does the drawn label *fit its box*?". Ukrainian/German/Polish run 15–30 % longer than English and Scaleform widgets **clip rather than shrink**, so a correctly-spelled translation still ships as a truncated button. `FontMetrics.measure(text, font_px)` sums `font_checker`'s per-glyph advances (`Σ advance_em × font_px`) — the same summation the renderer does, minus kerning pairs (a sub-1 % effect that errs toward *under*-reporting, never inventing overflow). **The measurement is exact; the budget it is compared against is a model, and the two are kept distinct**: `WidgetSpec.confidence` is `MEASURED` (bounds **and** font size from the game's SWF), `DERIVED` (bounds from the SWF, size inferred from box height) or `ESTIMATED` (neither — a plausible default). `WidgetSpec.from_text_field()` turns a `swf_widgets.TextField` into a real, measured spec, and `load_metrics_for_family()` resolves its fontconfig family (`RF_55_M`) straight to the bundled TTF — so with a game folder loaded, **nothing is guessed**: not the width, not the size, not even the weight. It returns `None` for faces we don't ship and for **icon fonts** (`Genesis Controller Buttons` — a controller-glyph field is not text and must never be width-checked), so the caller says "cannot measure" instead of measuring with the wrong font. The two HUD presets in `WIDGETS` are `MEASURED` (read from `hudmessagesmenu › QuestObjectiveText_tf` = 335px @ 18px and `hudmenu › PromptMessageWidget.textField` = 317px @ 19px — both had been guessed far too generously, the objective at 480px); the rest are still `ESTIMATED` and say so. Every budget is user-editable, and every `FitResult` also carries `source_ratio` — the translated width ÷ the English width, which needs no budget at all and is the strongest signal available (the English fit *by construction*, since Bethesda laid the widget out around it). `WIDGETS` covers only **length-critical** single-line widgets (button/tab/menu label/item name/HUD objective/notification/tooltip title) — wrapping widgets (dialogue, books, notes) grow downward instead of clipping, so width is not their failure mode and flagging them would be noise; `is_length_critical()` enforces that gate even under a `widget_override`. `render_text()` resolves markup before measuring: formatting tags (`<font>`, `<br>`) contribute 0 px, while **value** placeholders (`<Alias=…>`, `%s`, `<mag>`) are replaced by a representative sample — measuring the literal `<Alias=Player>` is nonsense and deleting it under-measures, so results carrying one are flagged `is_approximate`. `uppercase` widgets are measured after the CAPS transform they actually draw with; font **role** matters too (`NB_Architekt` has *no* Cyrillic, and semibold `RF_55_SB` is ~19 % wider than `RF_35_M`, so measuring a bold button with the regular face under-reports overflow). `load_bundled_metrics()` reads the real Starfield faces committed under `data/fonts/`, so the tool needs zero configuration and still uses genuine game metrics. Pure Python (no Qt). Front-ends: `width_fit_dialog`, and the live indicator in `visual_context_preview`.

**`gui/`** — PySide6 application layer:

#### Core window & table
- `main_window.py` — `MainWindow`: top-level window. Owns the worker thread, file-open/save logic, audit log, crash recovery, and coordinates all other components.
- `string_table.py` — `StringTableModel` / `StringTableView`: `QAbstractTableModel` with two display modes — `"strings"` (for `.strings`/`.dlstrings`/`.ilstrings`) and `"esp"` (for ESP/ESM). Column layout differs between modes. Emits `Ctrl+C/V/Shift+C/Shift+V` clipboard shortcuts and a status-bar `Total/Done/Left %` + ETA label during batches. `Delete` clears the selected rows' translation and reverts status to pending (`clear_translations`); `apply_to_identical(row)` copies one row's translation to every row with the same source (Translation → "Apply Translation to All Identical Originals", `Ctrl+Alt+D`). `import_translations(translation_map, source_map=None, only_pending=False)` fills rows by ID then source text; `only_pending=True` leaves rows that already carry a non-empty translation untouched (used by the Official-TM miner import so in-progress work is never clobbered).
- `app_settings.py` — `AppSettings` dataclass (`CONFIG_VERSION = 43`). Persisted as JSON (primary) + `QSettings` (secondary). Entry points: `load_settings()` / `save_settings()`. Also owns the canonical **`SUPPORTED_LANGUAGES`** table (`(display name, Starfield locale code)`) that both `main_window` and `settings_dialog` render their source/target pickers from, plus `LANGUAGE_NAME_TO_CODE` / `LANGUAGE_CODES`. It lives here because two private copies drifted: `default_source_lang`/`default_target_lang` hold the **code** (`"uk"`) — every consumer keys off it (`_TARGET_STYLE`, `_GENDERED_TARGETS`, `preload_language_dictionaries`) and silently ignores an unrecognised value rather than rejecting it — but the Settings dialog kept a four-name list whose combo items carried the *display name* as their data, so it offered 4 of 12 languages, wrote `"Ukrainian"` back over `"uk"` (undoing the v20 migration), and wrote **`None`** when its `findData(code)` matched nothing and left the combo at index −1 (which then raised in the TMX loader on `default_source_lang[:2]`). The v43 migration repairs both cases in existing configs; `test_language_settings.py` pins the contract. `nexusmods_api_key` is XOR+base64 obfuscated on disk via `_obfuscate()`/`_deobfuscate()`; in-memory value is always plaintext. `mcp_servers` is a nested list (not a top-level string), so it can't ride `_OBFUSCATED_FIELDS` — `_obfuscate_mcp_entry`/`_deobfuscate_mcp_entry` wrap only each entry's `authorization_token` (same `enc:` XOR scheme), wired into `to_dict`/`from_dict`.
- `settings_dialog.py` — full settings UI (backend selector, model, keys, QC options, NexusMods, Audio/TTS, shortcuts, etc.). Includes a **Claude MCP Servers** group (`chk_enable_mcp` + a Name/URL/Auth-token `mcp_table` with Add/Remove buttons); `_collect_mcp_servers()` reads the table, drops rows missing a name or URL, and writes `AppSettings.enable_mcp`/`mcp_servers` in `apply_to_settings`.
- `theme_manager.py` — built-in QSS themes (`Slate`, etc.) + custom theme support. Applied as application-wide stylesheets.
- `theme_dialog.py` — theme picker/editor dialog.

#### Translation backends
- `ollama_worker.py` — `OllamaWorker`: runs in a dedicated `QThread`. Uses a `ThreadPoolExecutor` (default 10 workers) to call the Ollama HTTP API in parallel. Emits `translation_ready(index, text, string_id)`, `progress`, `error`, `finished`. Contains `_restore_dropped_tags()`: post-translation safety net that re-inserts Bethesda game tags (`<mag>`, `<dur>`, `<area>`, etc.) that the model dropped, using fractional position heuristics.
- `claude_client.py` — shared Claude API client (translation, chat, quality review). Manages API key via `SecretStore`. Model registry: Haiku 4.5 (default), Sonnet 4.6, Opus 4.8. All requests go through `_create_message()`, which applies **exponential-backoff retry on 429/5xx** (rate-limit / transient) errors — honouring a `Retry-After` header when present, jittered otherwise, capped at `_MAX_RETRIES`; the SDK's own auto-retry is disabled (`max_retries=0`) so the two don't compound. Non-retriable errors (auth, 4xx≠429) propagate immediately. Also holds the **Messages API MCP connector** (beta header `_MCP_BETA = "mcp-client-2025-11-20"`): `__init__` takes an optional `mcp_servers` list; `_mcp_request_kwargs()` shapes each configured server into the paired `mcp_servers=[{type:"url", url, name, authorization_token?}]` + `tools=[{type:"mcp_toolset", mcp_server_name}]` the API requires (rows missing a name or URL are skipped; empty → `{}` so the caller falls back to a plain call); `chat_mcp(messages, system, on_tool=…)` runs a non-streaming loop that appends text blocks, reports each `mcp_tool_use` block name via the `on_tool` callback, and resumes multi-round tool turns on `stop_reason == "pause_turn"` by echoing the assistant turn back (capped at 8 rounds). Anthropic makes the MCP connection and runs the tools server-side.
- `claude_code_client.py` — `ClaudeCodeClient`: subscription-backed **drop-in for `ClaudeClient`** that shells out to the local `claude` CLI (`-p --output-format json --model <alias> --system-prompt … --strict-mcp-config`, prompt on stdin) instead of the metered Anthropic API — for users who don't want to pay Claude API usage. Same public surface (`translate`/`chat`/`chat_stream`/`chat_mcp`/`review_translation`) so the translation worker and chat panel use either client interchangeably. Model ids are `claude-code:<tier>` (`haiku`/`sonnet`/`opus`); `is_claude_code_model()` routes them here and `cli_alias_for()` maps the id to the CLI `--model` alias. `find_claude_cli()` locates the binary (honours `CLAUDE_CLI_PATH`); `claude_code_available()` gates the UI. `_invoke()` **strips `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` from the child env** so the CLI always uses subscription (OAuth) auth and never silently bills the API, and runs in an empty scratch cwd so no project `CLAUDE.md` is auto-discovered. `--system-prompt` replaces Claude Code's coding-agent prompt (clean translator, no tools); MCP/streaming don't apply (`chat_stream` yields one chunk, `chat_mcp` delegates to `chat`). #### Translation pipeline helpers
- `term_protector.py` — `TermProtector`: replaces protected terms with unique placeholder tokens before AI calls, restores them after. Terms are matched with one combined regex rather than a loop. The default set is small and deliberately so — 20 `STRUCTURAL_PATTERNS`, 3 `CONTEXT_PATTERNS` and 86 built-in proper nouns — because `protected_terms_starfield_hq.txt` was emptied on purpose (commit `4e487c7`: Starfield's faction/company/UI terms are all meant to be translated) and is now untracked entirely — a user extension point, not a bundled 8k-term list. `STRUCTURAL_PATTERNS` also locks **deliberately-obfuscated in-game codes** (encrypted notes, passwords, scrambled terminal text — garbage by design, e.g. `VH1QCR4P$KU`, `WWFX`): `obf_code` (ASCII alnum run + symbols `$ # @ ^ ! ' ~`, qualified by ≥1 letter and ≥1 *digit-or-strong-symbol* `$ # @` — weak symbols `^ ! ' ~` never qualify a token on their own, so `don't`/`Hello!`/`$500` are left alone) and `obf_acronym` (all-uppercase vowel-less run; vowel-bearing acronyms like `DNA`→`ДНК` stay translatable). Overlap is resolved longest-span-wins, so `obf_code` beats the shorter `chemical_formula`/`form_id` on the same token.
- `translation_cache.py` — `TranslationCache`: thread-safe JSON-backed cache keyed on `sha256(text + model + source_lang + target_lang)`. Capped at `DEFAULT_MAX_SIZE = 100,000` entries.
- `translation_memory.py` — `TranslationMemory`: pre-loaded map of string ID → correct translation from a prior file. Consulted before any model call so known strings are never retranslated. Persists as a **JSON snapshot** (`save_snapshot`/`load_snapshot`, id keys stored as hex) so a loaded TM survives across sessions without re-importing the source TXT/TMX; `main_window` auto-loads it on startup, re-saves on TM-load and on close, and keeps the canonical `TranslationMemory` on the window (re-attached in `_init_translation_worker`) so a worker rebuild never drops it. `entries()` feeds the browser dialog. `add_pairs(pairs, *, prefer_existing=False)` merges `(source, target)` pairs into the source-keyed map (used by the Official-TM miner, which has no string IDs — matched by source text). Fuzzy lookup (`get_fuzzy`) is guarded by a **digit-run check** in `fuzzy_match.best_fuzzy_match` (a match whose numeric runs differ from the source — `28LY` vs `30LY`, `Level 3` vs `Level 5` — is rejected), and narrowed by a lazily-built `fuzzy_match.FuzzyIndex` (rebuilt under a lock after any write to the source map, since `get_fuzzy` runs on every worker thread at once). **`__len__`/`__bool__` count both indexes** — reading only `_by_id` reported a TMX-loaded or miner-mined memory as empty, and five separate gates test exactly that (worker attachment, the lookup gate in both backends, snapshot-on-exit, the browser, the status-bar indicator), so a source-keyed TM was silently switched off everywhere.
- `tm_browser_dialog.py` — `TMBrowserDialog`: searchable read-only table of the loaded TM (ID / Source / Translation), live-filtered across all three columns. Opened from Translation → "Browse Translation Memory…" or by clicking the status-bar **TM indicator** (`_tm_lbl`, shown only when a TM is loaded).
- `glossary.py` — `GlossaryManager`: CSV/TBX/JSON I/O, suggest dock, AI prompt injection, GLOSSARY_MISMATCH QC check.
- `glossary_editor.py` — full-screen glossary editing dialog.

- `ko_particle_checker.py` — Korean 조사 (particle) agreement, computed not guessed: Hangul syllables decompose arithmetically, so `(ord(ch) - 0xAC00) % 28` gives the 받침 (final-consonant) index and the correct allomorph follows exactly. Two checks, both wired into `QualityChecker` (`_check_ko_particles`, gated on `_HANGUL_TARGETS`; the module and its word list are imported lazily so non-Korean targets never load them) and both in `AUTOFIX_CODES` via `fix_particles()`. **`check_placeholder_particles` (`KO_PARTICLE_PLACEHOLDER`)** — sound, no dictionary: a single-form particle after a *value* placeholder (`<Alias=…>`, `<mag>`, `%s`, `{name}`) is always a latent bug, since the substituted noun's 받침 is unknown at translation time and the engine does no particle resolution; the fix is the both-form (`<Alias=Player>은(는)`, `%s이(가)`, `(으)로`). Formatting tags (`<b>`, `<br>`, `</font>`) are deliberately not placeholders — they wrap known text. **`check_batchim_particles` (`KO_PARTICLE_MISMATCH`)** — verifies a particle against its Hangul stem, restricted to the provably sound subset because there is no POS tagger: only the 은/는 and 을/를 pairs (`BATCHIM_PAIRS`), because `가`/`과`/`로` are productive Sino-Korean noun suffixes (`모험가`, `효과`, `반응로` are single nouns, not stem+particle, and no word list enumerates them); plus three guards — token not itself a dictionary word (`없는`, `가을`), stem *is* a dictionary word, and stem ≥ 2 syllables (`-는` is also the adnominal verb ending, and verb stems are overwhelmingly one syllable or vowel-final). Silent when `data/korean_words.txt` is missing — it refuses to guess, since the auto-fixer acts on what it reports. Measured at 0 false positives over 5,353 real Korean strings. The same rules are taught to the model in `_TARGET_STYLE["ko"]` (read acronyms aloud in Hangul — `O2` → 오투 → `O2는`; `H3` → 에이치삼 → `H3은` — never from the Latin spelling).
- `gender_dialog.py` — `GenderDialog`: displays gender mismatch results, inline fix suggestions.
- ти/ви register consistency is **not** a separate post-hoc check — it is enforced inline by the translation system prompt (`_TARGET_STYLE["uk"]` in `ollama_worker.py`, shared by both backends via `TranslationRequest.to_system_prompt()`), which instructs the model to keep informal ти / formal ви consistent per speaker and never mix the two (incl. possessives твій/ваш).
- **Player-gender-aware translation**: English `you`/adjectives don't encode grammatical gender but many targets do, so a player-referring line («You are ready.») needs a gender the source doesn't supply. `AppSettings.player_gender` (`""`=unspecified / `"male"` / `"female"` / `"neutral"`, editable in **Settings → Translation Preferences** and the **Prompt Editor**) is installed into `ollama_worker` via `set_player_gender()`/`get_player_gender()` (a **separate** module-level layer, deliberately NOT folded into the `get_prompt_customizations()` 3-tuple so its tested `== ({}, "", {})` contract is unchanged). `_player_gender_directive(target_lang)` emits a strong prompt line (masculine/feminine forms, or gender-neutral phrasing for `"neutral"`) — injected by `to_system_prompt()` in **both** normal and fix-mode paths, and **only** for gendered targets (`_GENDERED_TARGETS = {de,es,fr,it,pl,ptbr,ru,uk}`; a no-op for en/ja/ko/zhhans). Installed at the single `main_window._apply_prompt_customizations()` hook (startup + after Settings/Prompt-editor saves). Because a `.strings` file stores one text per ID, the choice applies to the whole translation for every player (no runtime M/F switch) — hence the `"neutral"` option for all-player mods. `gui/player_gender.py` (pure, no Qt) `is_player_referring()`/`find_player_referring_rows()` flag which source strings are gender-sensitive (2nd-person pronouns + `<Alias=Player>`/`[PLYR]`); Translation menu → "Find Player-Referring Strings" selects them. Front-ends: `settings_dialog`, `prompt_editor_dialog`.
- **Pre-batch player-gender nudge**: an unset gender is only a *problem* when the batch actually contains player-referring lines and the target inflects — so the warning fires there, not as a post-hoc `QualityChecker` code (by then the AI has already guessed a gender per line, and paid for it). `main_window._check_player_gender_nudge(requests)` gates `_start_translation()` (the single choke point for both Translate Selected and Translate All, just before the Claude pre-flight) and returns False to cancel the batch. It bails out early — costing nothing on the common path — unless all four hold: `AppSettings.warn_player_gender_unset` is on, `player_gender` is unset, `ollama_worker.is_gendered_target(target)` (the public predicate over `_GENDERED_TARGETS`), and `player_gender.count_player_referring_texts()` over the *requests'* source texts (not the whole file) is non-zero. The dialog offers **Set Gender…** (`_quick_set_player_gender()` — a `QInputDialog` picker that writes `player_gender`, re-runs `_apply_prompt_customizations()` so the pending batch picks it up at prompt-build time, and cancels the batch if dismissed, so the choice can't be skipped by accident) / **Translate Anyway** / **Cancel**, plus a "Don't warn me again" checkbox that clears `warn_player_gender_unset`.
- `spell_checker.py` — multi-backend spell checker: Hunspell (via ctypes), spylls (pure Python), or CLI fallback. Used by the font checker and as a standalone QA step.
- `font_checker_dialog.py` — scans translations for characters absent from the game's Scaleform SWF font atlases.
- `width_fit_dialog.py` — `WidthFitDialog` (Translation menu → "UI Width-Fit Simulator…", `_open_width_fit`): front-end for `bethesda_strings.width_fit`. Defaults to the bundled Starfield fonts (a game SWF/TTF can override; a font with glyphs but **no** advance table is *refused* with an explanation rather than silently measured with invented widths). A **"Real Widgets from the Game"** group takes a Data folder and runs `swf_widgets.scan_game_ui` on a `QThread` (`_CatalogueWorker` — ~250 SWFs, too slow for the UI thread), then lists the deduped **clipping** fields in a type-to-filter combo (only those whose font we ship metrics for — icon-font fields are dropped, not mis-measured), marking `~` where the font size was inferred rather than declared. Picking one overrides the budget, the font size **and** the face for the scan. A **"Check the tightest build"** checkbox (on by default) swaps the chosen widget for its tightest build via `catalogue.worst_case_with_reason()`, and the info line (`_variant_note`) reports **all four** outcomes rather than only the swap — it **names the build** it measured (not "the large-font build", since 2 shipped widgets shrink the font there), says when the twin is no tighter, distinguishes "this widget *is* the large-font build" from "this menu ships none", and warns **⚠ not checked** when the pairing was ambiguous. Silence on the last of those would let the user believe a widget was covered when it never was. This is what catches the translation that passes the normal menu and clips only for players using the large font — e.g. «Розташування корабля» fits `shipcrewmenu › Location_tf` at 18px (61 %) but hits 122 % in `shipcrewmenu_lrg` at 36px, in the same 264px box. #### NexusMods integration
- `nexusmods_sso.py` — NexusMods Single Sign-On client. Their API Acceptable Use Policy (help.nexusmods.com/article/114) forbids public apps from using pasted *personal* API keys; SSO issues a per-user key through the browser instead. Minimal RFC-6455 WebSocket client over stdlib `socket`/`ssl` (no third-party dep, so it works in the frozen build): connects to `wss://sso.nexusmods.com`, sends `{id, token, protocol:2}`, opens `https://www.nexusmods.com/sso?id=<uuid>&application=<slug>` in the browser, and returns the `api_key` the server pushes after the user authorises. `encode_frame`/`decode_frame`/`build_sso_url` are pure (unit-tested in `test_nexusmods_sso.py`). `request_api_key(on_url, slug, connection_token, …)` is driven from `settings_dialog` via `_NexusSSOWorker` (a `QThread`); the reusable `connection_token` is persisted as `AppSettings.nexusmods_sso_token` (obfuscated). The `application` slug must be a slug **registered/approved by NexusMods staff** — the SSO web page validates `?application=<slug>` and shows "Application ID was invalid" for any unregistered value (protocol-2 validates browser-side, so an unregistered slug never errors over the WebSocket — it just times out). The slug is therefore configurable: `AppSettings.nexusmods_sso_slug` (Settings → NexusMods → "SSO App Slug"), or the `NEXUSMODS_SSO_SLUG` env var, or the per-call `slug=` arg; blank falls back to `APPLICATION_SLUG`, whose built-in default `_DEFAULT_SLUG = "0xra-bethesdastringseditor"` is the **registered, staff-approved slug** (pinned by `test_nexusmods_sso.test_default_slug_is_the_registered_one`). **SSO is the only key-acquisition path** — per the AUP requirement, there is no manual personal-API-key entry field anywhere in the app. `settings_dialog` shows Sign in / Sign out + a signed-in/not-signed-in status; the SSO-issued key lives in `self._nexus_api_key` (never an editable widget) and is persisted to `AppSettings.nexusmods_api_key` (obfuscated). The SSO key is consumed by the browser/download paths; the release CI uploads with its own `NEXUSMODS_API_KEY` repo secret and never touches user settings.

Driven by `main.py --register-file-types` / `--unregister-file-types`, handled before Qt loads. `main.py` has always opened `sys.argv[1]`, so only the registration was ever missing — and PyInstaller cannot do it (an OS action, not a packaging one), which is why the spec bundles `packaging/*` for this module to read out of `sys._MEIPASS`. Split into **plan** (pure functions: `windows_registry_plan`, `desktop_entry_text`, `icon_targets`, `launch_argv`) and **apply** (`install_linux`/`install_windows`), so the Windows registry layout is unit-tested on Linux CI — a wrong ProgID or an unquoted `%1` yields an entry Explorer accepts and then fails to launch, logging nothing. Linux installs icons in **two contexts** (`apps/` backs the desktop entry's `Icon=`; `mimetypes/` is what the file manager draws per file) and, within `mimetypes`, under **two names** — the one the MIME XML declares and each type's dashed name (`application/x-bethesda-strings`) — because GIO tries them in that order and stops at the first hit. Intermediate sizes (16/22/24/32/48/128/256) come from Pillow when importable; the frozen build excludes Pillow, so releases install the two shipped sizes and let the toolkit downscale. Thunar caches icons for its daemon's lifetime, so it is restarted. Windows writes `OpenWithProgids` always but claims the extension's **default** only under `--force`: Windows 10+ guards a user-chosen default behind a UserChoice hash no app may forge, and silently taking `.esp` from a modding tool the user picked is worse than not being the default. Front-end: `scripts/install_file_associations.sh`.
- `fuzzy_match.py` — Levenshtein distance, longest common substring/prefix, word-level distance, unicode control char utilities. Used by advanced search and consistency checker. `FuzzyIndex` is a **sound** candidate pre-filter for `best_fuzzy_match` (a linear scan costing a tokenisation + word-edit-distance per entry, i.e. ~90 ms per lookup against a six-figure mined TM, on the path every uncached string takes): it drops only candidates `fuzzy_score` would have rejected anyway, from two of that function's own bounds — a multi-word source must match `n - threshold + 1` positions (so the query-side multiplicity of the shared words is an upper bound on reachability) and the candidate's word count is capped at `n + threshold`; a **single-word** source takes the substring path, which can match without sharing a word (`Reload`/`Reloads`), so those are indexed by **length** instead, within `_substring_threshold_inc`. Candidates come back in **insertion order** — `best_fuzzy_match` keeps the first candidate at the best score, so returning a set would make ties resolve differently per run (`PYTHONHASHSEED`) for the same memory and string. ~10× faster, byte-identical results.
- `en_word_checker.py`, `ru_word_checker.py`, `uk_word_checker.py`, `de_word_checker.py`, `fr_word_checker.py`, `es_word_checker.py`, `pl_word_checker.py`, `it_word_checker.py`, `ptbr_word_checker.py`, `ko_word_checker.py` — word-list-based detectors for untranslated source-language text in output. All extend `_word_checker_base.py`. Word lists are in `data/`. They are **preloaded per language pair**, not wholesale: `ollama_worker.preload_language_dictionaries(source, target)` (called at the start of each batch by both backends) warms the pair plus English (English-leak check + English-text protection) plus Russian for a Ukrainian target (Russian-leak check). Loading all nine unconditionally cost ~330 MB of resident set — a 35 MB Russian list alone — for languages a session never touches; an EN→KO session now pays ~44 MB. `WordChecker.preload()` is idempotent and spawns no thread once loaded. Korean uses `min_word_len=1` (a Hangul syllable block is a whole syllable) and keys off Hangul script presence before falling back to the frequency list.

### Key design notes

- **Native file dialogs are disabled** via `Qt.ApplicationAttribute.AA_DontUseNativeDialogs` (set before `QApplication` is created). This is intentional — GTK/KDE portal dialogs deadlock the Qt event loop on Linux tiling WMs.
- **Translation backend selection**: chosen by the **model name** in `AppSettings.ollama_model` (there is no separate backend flag). `main_window._init_translation_worker()` routes `is_claude_model(model)` (anything starting `claude-`, which includes `claude-code:*`) to `ClaudeTranslationWorker`, else `OllamaWorker`; the Claude worker then picks the API vs CLI client via `is_claude_code_model(model)`. `OllamaWorker` and `ClaudeTranslationWorker` implement the same signal interface. The `claude-code:*` (subscription CLI) backend shows a **token-only** pre-flight estimate (`_claude_preflight_check(requests, subscription=True)` — counts, no misleading USD figure) instead of the API's cost estimate, skips the Ollama server-restart (no local server), and is capped at 3 concurrent workers (one subprocess per request). It also reports **actual** token usage after each batch: `ClaudeCodeClient` accumulates the real `usage`/`total_cost_usd` the CLI returns per call (thread-safe; `reset_usage()`/`get_usage()`), `ClaudeTranslationWorker` resets at batch start and emits `usage_ready(dict)` before `finished`, and `main_window._on_translation_usage` → `_on_ollama_finished` shows the totals (`_format_usage_message`) in a toast + status bar (equivalent cost labelled "not billed").
- **Translation pipeline per string**: `TermProtector.protect()` → model API call → `TermProtector.restore()` → `_restore_dropped_tags()` → `QualityChecker` → emit `translation_ready`.
- **Prompt customization (Translation Prompt Editor)**: three layers feed the system prompt. (1) **Tuning dials** — `PROMPT_DIALS` (a spec list of `{key, label, multi, default, options:[(key,label,instruction)]}`) drives both the UI and `build_dials_prompt(dials)`, which renders a "Translation preferences:" bullet block from only the non-default/checked choices (neutral options carry an empty instruction so they add nothing). (2) **Rule 1** (target-language style/register, from `_TARGET_STYLE`) overridable per language. (3) A free-text **addendum** appended to every prompt. State lives at module scope in `ollama_worker.py` (`_CUSTOM_STYLE_OVERRIDES`, `_CUSTOM_PROMPT_ADDENDUM`, `_CUSTOM_PROMPT_DIALS`), installed via `set_prompt_customizations(style_overrides, addendum, dials)` and snapshotted via `get_prompt_customizations()` (returns a 3-tuple; dial lists are deep-copied). `default_style_rule(lang)` / `effective_style_rule(lang)` resolve built-in vs overridden Rule 1. `to_system_prompt()` reads this state (normal **and** fix-mode paths — dials block then addendum, after examples/glossary/profile), so customizations ride through without threading values into the many `TranslationRequest` constructors, and every backend honours them. Persisted as `AppSettings.custom_style_rules` (dict) + `custom_prompt_addendum` (str) + `custom_prompt_dials` (dict); `main_window._apply_prompt_customizations()` installs them at startup and after Settings/editor saves. The token-preservation rules (2–7) are never user-editable. Front-end: `prompt_editor_dialog`.
- **Game tag restoration**: `_restore_dropped_tags()` in `ollama_worker.py` re-inserts Bethesda variable placeholders (`<mag>`, `<dur>`, `<area>`, `<relat>`, `<basename>`, `<repetitions>`, `<N.Prop>`) that the model drops. Uses fractional-position heuristics: `frac ≤ 0.15` → prepend, `frac ≥ 0.92` → append, `0.70 ≤ frac < 0.92` → insert before last token (handles `<dur>с` ordering), `else` → walk to next word boundary. Sign-prefixed tags (`+<mag>`, `-<mag>`) have the sign preserved.
- **English-text protection (non-English source → target)**: `_protect_english_text()` in `ollama_worker.py` runs only when `protect_english_text` is on and `source_lang != "en"` (e.g. a full Russian localization → Ukrainian). It protects ALL-CAPS game codes/acronyms and lowercase English content words (dictionary-checked via `en_word_checker`), but **deliberately does NOT protect bare Capitalised proper nouns** — character/planet names must transliterate into the target script, not stay English. To pin an exact spelling, add the name to the **glossary**: `_glossary_localize()` (Phase 0, runs before the per-word scan) substitutes each glossary hit's `target_term` deterministically (no model call) behind the same `__EN……__` restore token, so multi-word names like `Sarah Morgan → Сара Морган` are handled and a glossary entry beats even ALL-CAPS protection. The Claude backend has no equivalent path (this is Ollama-only). Tests: `test_ollama_english_protection.py`.
- **Config location**: JSON config file is written to a platform-appropriate config directory (see `get_config_path()` in `app_settings.py`), not the project root.
- **API key obfuscation**: `nexusmods_api_key` is stored in the JSON config as `enc:<base64(xor(value, fixed_salt))>`. Legacy plaintext values (no `enc:` prefix) are still read correctly.
- **Claude API key**: stored exclusively via `SecretStore` (system keyring or AES-256-GCM file), never in the JSON config.
- **Protected terms file**: `protected_terms_starfield_hq.txt` in the project root is an optional user-supplied terms list, read at startup when present. It is **not tracked and not bundled** — the app ships without one and falls back to `TermProtector`'s built-in set. `starfield_glossary.json` is likewise untracked: it is a build artifact of `scripts/extract_starfield_glossary.py` that no code ever opens by that name (`GlossaryManager` reads `<config>/glossary.json`).
- **Drag and drop**: `_DropOverlay` + `_WelcomeWidget` on the main window; green/red feedback; extension validation; `dragMoveEvent` required to prevent forbidden cursor.
- **NexusMods search**: primary path is `api.nexusmods.com/v2/graphql` (GraphQL `nameStemmed: MATCHES`); fallback to `search.nexusmods.com` (Elasticsearch, may fail DNS on some networks).
